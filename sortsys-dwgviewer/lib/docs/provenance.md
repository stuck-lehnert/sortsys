# DWG Parser Provenance

This directory records where nontrivial constants, tables, and format behavior came from.

- DWG version identifiers such as `AC1015`, `AC1027`, and `AC1032` are public file header markers used by AutoCAD DWG files. The initial table in `dwgfile` maps those public identifiers to release-family labels for diagnostics only.
- The local reference `sortsys-dwgviewer/spec/OpenDesign_Specification_for_.dwg_files.pdf` is the Open Design Alliance “Open Design Specification for .dwg files”, version 5.4.1. It is used as the source for DWG bit-code definitions, modular integer behavior, R13-R2000 section locator records, fixed object type IDs, handle references, R2004/R2007 layout metadata, security flags, and the R2004 LZ77-style decompression rules.
- The R2004+ page-map sentinel in `dwgfile` was originally treated as a fixture-observed file-structure marker from local AC1018, AC1024, and AC1032 DWG samples. Future work should prefer decoded page/header metadata from the local ODA specification over sentinel probing when that metadata is available.
- R2004 section reconstruction follows the local ODA specification chapters for the encrypted 0x6c file-header data, global section page map, data section map, encrypted data page headers, and R2004 LZ-style section compression. The implementation resolves local section page records through the global page map instead of scanning candidate page headers.
- R2004 compressed literal length byte 0x0f is accepted as a fixture-observed extension/erratum to the local ODA text: the text says 0x01-0x0e but also says the direct literal range reaches 0x12 bytes, which requires accepting 0x0f as length 18.
- R18 AcDb:Handles location offsets are treated as chunk-local accumulators based on local AC1018 fixture behavior. Handle deltas remain cumulative across chunks; location deltas reset at each chunk boundary so all offsets resolve inside AcDb:AcDbObjects.
- AC1024/R2010, AC1027/R2013, and AC1032/R2018 are routed through the R2004-style page-map reconstruction path based on the local ODA specification statement that these versions reuse the R2004 file header, page map, section map, and compression organization. AC1021/R2007 remains the distinct Reed-Solomon container family.
- AC1024/R2010 compact entity payload offsets for direct `LINE`, `ARC`, `CIRCLE`, `POINT`, `ELLIPSE`, and `LWPOLYLINE` decoding are fixture-observed against the local RDAI AC1024 drawings in `/var/home/gunter/Downloads/dwg-cat-plan-refs`. The entity field order itself follows the local ODA specification; the candidate offsets account for compact common-data layouts before the entity-specific payload and are guarded by pre-handle bit-boundary checks.
- AC1032/R2018 compact `LWPOLYLINE` payload starts 82/146/154/128/252 and paired fallback starts 98/162/170, plus compact `LINE` starts 132/196/146/252/80, are fixture-observed against `/var/home/gunter/Downloads/dwg-cat-plan-refs/250724_GA+CAFFE_AMBURGO_NEUER_WALL_42_2025.dwg`. These candidates preserve the local ODA entity field order; they are accepted only after bounded-coordinate/entity-shape validation and a bounded pre-handle trailing-bit check.
- R2010 `BLOCK_HEADER`/`INSERT` expansion uses the local ODA handle-reference model and block-header handle-stream ordering, with child entities accepted only between resolved `BLOCK` and `ENDBLK` records. Compact INSERT placement offsets are fixture-observed against the same local AC1024 RDAI drawings, and expansion is intentionally limited to references that resolve to known `BLOCK_HEADER` objects.
- SPLINE field order follows the local ODA SPLINE entity description for scenario, degree, fit-point data, control-point data, knots, and optional weights. The current viewer projection emits decoded fit/control points as a smooth browser curve path and does not yet claim exact NURBS evaluation.
- Simple HATCH boundary extraction follows the local ODA HATCH field order for line, polyline, circular arc, elliptical arc, and spline boundary path records. R2010 compact HATCH payload offsets 73/81 are fixture-observed against local AC1024 RDAI hatches and are accepted only when the decoded loops contain finite, bounded coordinates. The no-gradient preamble fallback is fixture-observed against local AC1024 RDAI hatches and is kept conservative: unaligned hatch bodies remain unsupported diagnostics rather than guessed geometry.
- R2007+ `TV` text extraction follows the local ODA string-stream description: text bytes are stored as UTF-16 strings in the object string stream, whose presence flag and bit-length suffix live immediately before the handle stream. AC1024/R2010 compact payload offsets for `TEXT`, `MTEXT`, `ATTRIB`, and `ATTDEF` are fixture-observed against the local RDAI drawings and are accepted only when the entity payload ends before the string stream and yields bounded coordinates, positive text height, and non-empty text.
- AC1018/R2004 `LWPOLYLINE` fallback payload offsets 150/142/70 are fixture-observed against the local Hermès general-plan drawing and are accepted only after finite-coordinate and non-degenerate-extent validation. LWPOLYLINE field order and bulge semantics follow the local ODA specification/public CAD convention where bulge = tan(included angle / 4); bulged segments are carried into the scene schema as segment bulges so the browser renderer can draw circular arc segments directly. The offsets compensate for common entity display-data variants observed in that file.
- LWPOLYLINE OCS-to-WCS projection uses the local ODA extrusion/elevation field definitions and the public CAD arbitrary-axis convention: a normalized extrusion vector defines the OCS Z axis, the OCS X axis is derived from world Z unless the normal is close to world Z, and OCS `(x,y,elevation)` points are projected before 2D scene emission.
- AC1018/R2004 single-byte TEXT/MTEXT strings are decoded with a Windows-1252-compatible byte mapping when no R2007+ Unicode string stream is present. This follows the fixture-observed Western text encoding used in the local Hermès drawing and prevents invalid bytes from becoming JSON replacement characters.
- AC1018/R2004 `HATCH` fallback payloads are fixture-observed against the local Hermès general-plan drawing. These records decode with the normal ODA HATCH body layout when started two bits before the decoded display-data boundary; candidates are accepted only when loops are finite/bounded and, where the object-data end marker is present, the body parser lands exactly on it.
- AC1018/R2004 `TEXT` fallback payload offsets 150/142 are fixture-observed against the local Hermès general-plan drawing and use the local ODA R2000+ TEXT field order. Candidate text payloads are accepted only when they produce bounded coordinates, positive text height, and non-empty text. Long-prefix R2004 TEXT records also try the decoded common-entity display-data boundary and the following byte, which recovers fixture-observed records whose graphic/common-data prefix is much longer than the fixed-offset cases.
- Entity color extraction follows the local ODA `CMC(B)`/entity-color description for R2004+ and the public ACI color-index convention. Basic ACI 1-9 colors use fixed CAD color names; R2004+ true-color/color-method payloads are read as bit-long RGB/method values; method byte `0xc2` is treated as RGB and fixture-observed method byte `0xc3` maps low-byte values through the public ACI index convention. AC1018 common entity display data has five fixture-observed pre-color flag bits before the entity color field; using that alignment recovers the Hermès gray/blue/orange/red/teal palette and avoids the earlier misaligned green false positive. Extended 10-249 ACI colors use an approximate hue/shade projection until the full independent layer/color table decoder is implemented.
